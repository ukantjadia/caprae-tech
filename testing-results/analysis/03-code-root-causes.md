# Code root causes: PageSpeed (mobile) and GTmetrix (desktop), capraetech.io, Oct 21

Source checked: `seo/code` at b871b69. The particle chunk `stage-B32UjMJF.js` rebuilds to the same hash, so it is byte-identical to what the reports tested. Home CSS and JS changed after the reports (b871b69), so CSS byte counts below are from the current build. Read-only investigation, nothing in the site was changed.

## Summary

1. The 25 s TBT, 39 s of main-thread work and 20 long tasks all come from one loop. It runs a GPGPU step, renders 10,000 instanced particles (480,000 triangles) and draws 13 bloom passes every frame, and it never stops. PageSpeed's lab Chrome ran it on software WebGL (SwiftShader), so every frame became a 400 to 975 ms CPU task.
2. That number is a test artifact. Chrome 139 and later no longer fall back to SwiftShader. GTmetrix (Chrome 154) got no WebGL context, so the engine exited before fetching `/shapes.bin`, and TBT was 40 ms. The engine has no software-renderer check (`failIfMajorPerformanceCaveat`). Its adaptive resolution counts frames rather than time, so at 2 fps it never adapts within the 30 s trace.
3. Real problems remain for real visitors. The loop never idles: it keeps running behind the footer, under reduced motion, and once the scene has settled. 54% of the home DOM (1,074 of 1,988 elements) sits in 20 hidden Lab variants, built by an inline script that is the ~0.5 s task before first paint. The h1 fades in from opacity 0. The non-composited loader fade defeats its own purpose.
4. Accessibility: the dev-shop column is #6e727a on black (4.35:1, below 4.5:1). The home page has no `<main>`. Pricing uses `h4` under an `h2`. Two "Book a call" links have the same name but different targets. All four are S-effort fixes.
5. The 38 inner pages run the same engine after the `load` event, with the same 10,000 particles and bloom. Expect the same TBT pattern on PageSpeed mobile. Inner CSS also carries the Lab's variant styles (`home-styles.css`, 36.5 KB raw).

## How the particle loop behaves

1. **Start, after first paint.** `home.js:28` calls `startStage` inside `requestAnimationFrame(() => setTimeout(...))`. On inner pages, `inner.js:18-20` imports `inner-stage.js` after `load`.
2. **Context or exit.** `stage.js:21` calls `new THREE.WebGLRenderer({ canvas, antialias:false, powerPreference:'high-performance' })`. If there is no WebGL (GTmetrix, Chrome 139+ without a GPU), three throws "Error creating WebGL context". The catch at `stage.js:22-25` removes the canvas and returns. **Nothing else runs and `shapes.bin` is never requested.** There is no `failIfMajorPerformanceCaveat` and no renderer-string check, so a software context (PageSpeed's lab Chrome) passes this step.
3. **Build.** `createField` (`stage.js:34`) streams `shapes.bin` (`field.js:97-105`; inner pages fetch `shapes/<set>.bin`), converts it to a float texture and sets up `GPUComputationRenderer` with a velocity and a position variable, each 100x100 float RGBA with ping-pong targets (`field.js:161-183`). It then builds the instanced mesh: 10,000 tetrahedral frames of 20 verts and 48 tris (`field.js:13-48,186`). `createDust` makes 250 more. `createPost` (`post.js:32-47`) builds RenderPass + UnrealBloomPass (5 mips) + the finish ShaderPass. `createTextMask` (`mask.js`) adds a 192 px wide 2D canvas texture, a MutationObserver on the whole body subtree and a ResizeObserver. `renderer.compile` (`stage.js:221`) compiles the field and dust shaders synchronously. This is the 975 ms task at 3.4 s in PageSpeed.
4. **Each frame** (`stage.js:156-220`):
   - JS: the scroll timeline (`stage.js:163-168`; inner pages rebuild `stopStates()` every frame, `stage.js:104-128`), group transform, camera ease, pointer speed. Then `document.querySelector('.cx-foot').getBoundingClientRect()` (`stage.js:205-206`). That is a layout read every frame, which forces layout whenever the typing rotor has changed the h1. D-068 says "no per-frame DOM reads"; this line contradicts it.
   - `mask.update(shift)` (`mask.js:43-56`): repaints the 2D mask and re-uploads the texture only when `scrollY` or the boxes changed.
   - `field.update` (`field.js:268-274`): `gpu.compute()` runs 2 full-texture shader passes. The velocity pass loops over all shapes per texel (`field.js:127-139`).
   - `dust.update`: sets a uniform.
   - `post.render` (`post.js:46`): the scene render (2 instanced draws, about 492,000 triangles; the vertex shader does 2 to 3 texture fetches and two sin-noise fields per vertex), then bloom (1 high-pass + 10 separable blur passes + 1 composite + 1 blend = 13 quads), then the vignette/grain pass to the screen.
   - Adaptive resolution (`stage.js:213-219`): every 90 frames, if more than 45 took over 20 ms, DPR drops by 0.15, down to 0.6. It counts frames, not seconds. It only cuts pixels, not the 10,000-instance vertex work or the bloom pass count, and it has no last step (bloom off, fewer particles, stop).
5. **What stops it.** Only the browser pausing rAF in a hidden tab or minimized window (`setAnimationLoop` is rAF-based). Nothing in the code stops or slows it:
   - It keeps running after the hero (by design, since shapes morph through the sections).
   - It keeps running when the footer pushes the canvas fully off-screen (`stage.js:206-207` only moves it).
   - It keeps running under `prefers-reduced-motion`, which freezes `t` (`stage.js:160`) but still computes and draws every frame.
   - It keeps running when the springs have settled. The 1 rad/s spin means a new image every frame anyway, except under reduced motion.
   - There is no IntersectionObserver, no `visibilitychange` handler and no idle detection.
6. **Why this becomes 25 s of TBT in the lab.** Under SwiftShader, the vertex work and the 15 full-screen passes run on the CPU. The renderer's WebGL calls block while the GPU process catches up, so each `frame()` is a 400 to 975 ms task attributed to `stage-*.js` ("Other" 38.3 s vs 0.6 s of script evaluation). There is never a quiet 5 s window, so TTI never arrives and TBT keeps adding up to the end of the trace.
7. **Side observers that add main-thread work later.** `mask.js:31-34` watches `class`, `open` and `style` on the whole body. Every footer-shift frame writes `canvas.style.transform` (`stage.js:207`), and `final-page.js:4` toggles `.in` on cards. Each of these schedules a re-measure that calls `getBoundingClientRect` on every text element (throttled to 250 ms). Minor.

## Inner pages

- All 38 inner pages run the same engine. `site/plugin.js:110` runs `particleStops` on every route except `/`, and `plugin.js:63` adds `data-shapes` to `<body>` (default set `brand`, `site/shapes.js:44`). `inner.js:18-20` imports `inner-stage.js` after `load`, which calls the same `startStage` (`inner-stage.js:10-24`) and the same `stage-B32UjMJF.js` chunk. The particle count is the same 10,000 (`SIDE` from `config.js:7`; `brand.bin` is 80,000 bytes = 10,000 x 4 x 1 shape x 2). Bloom and the text mask are the same.
- Expected on PageSpeed mobile: the same pattern. Long tasks start a little later (after `load` instead of after first paint), then continue to the end of the trace, so TBT should land in the same range. The `failIfMajorPerformanceCaveat` fix in `stage.js` covers all 39 pages at once. GTmetrix-style runs (no WebGL) should look clean on inner pages too.
- Differences from home: inner DOM is small (427 to 487 elements measured on pricing, why-founder-led, faq, work and how-it-works), and every inner page already has `<main>`. Inner CSS is larger: `inner-*.css` is 110 KB raw / 31.7 KB gzip, because `inner.css:12` imports all of `home-styles.css` (36.5 KB raw, including the Lab variant styles for cube, switch, before/after, slider, spotlight and so on) plus the full fontsource subsets. Expect a bigger "unused CSS" number there than on home. `pricing/index.html:34-35` repeats the `h4` heading-order issue, and `home-styles.css:159` repeats the contrast issue wherever the comparison table appears.
